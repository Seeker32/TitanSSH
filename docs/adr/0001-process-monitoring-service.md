# ADR-0001: 进程监控服务 — 独立 worker + 共享 exec 连接注册表

- 状态：已接受（2026-08-21）
- 关联：#36、ADR-0002

## 背景

process_service 是架构预留的第四个服务，需求是每会话持续进程采样（2 秒节奏、结构化快照事件推送），与现有主机监控（monitor_service）同构。接入前每个会话已有三条连接：终端、SFTP、监控采样专用 exec 连接。若进程监控再开一条独立连接，连接数随服务数线性增长（4 条/会话）。

约束：

- ssh2 的 `Session` 是 `Send` 但非 `Sync`，跨线程共享必须串行化。
- 架构规定服务隔离（no god service），monitor 与 process 的节奏、脚本、解析、失败语义必须可以独立演进。
- 采样节奏 2 秒、单次 exec 数十毫秒，串行化锁竞争可忽略。

可选方案：

1. 进程监控独立开第四条连接——简单，但连接数线性增长，且模式不可持续。
2. 合并两个采样循环为一个超级 worker、一次 tick 跑一个超级脚本同时产出主机指标与进程列表——连接天然只有一条，但两个服务的节奏、重试、失败语义被焊死，服务隔离名存实亡。
3. 传输层共享连接注册表：连接是纯基础设施，业务逻辑保持独立。

## 决策

采用方案 3：

- 传输层（ssh_transport）新增按 sessionId 键的**共享 exec 连接注册表**，底层 `Arc<Mutex<Session>>` 串行化 execute。
- monitor_worker 与 process_worker **各自保留独立的采样循环、采集脚本、输出解析与事件发射**，仅把连接注入缝从"自行建连"改为"从注册表解析连接"。
- 注册表连接的生命周期跟 session 走，session teardown 时回收。
- 共享命运：连接断开时，引用它的两个任务同时转 Failed——这是事实正确的行为，不做单任务静默重连遮掩。

明确拒绝方案 2：共享的只能是 TCP/SSH 传输这一纯基础设施（如同两个 HTTP 客户端共享一条 TCP 连接），不是业务逻辑。

## 后果

- 每会话连接数从 4 降为 3（终端、SFTP、共享采样连接）。
- 现有 monitor_worker 的注入缝需要一次性改造，既有 worker 测试的 mock 相应调整。
- 注册表是唯一新增测试缝，刻意保持极薄（insert / 取用 / 回收），业务逻辑测试一律注入"连接提供者"而不感知注册表存在。
- 将来终端、SFTP 也可迁入注册表——届时是纯传输层重构，不破坏任何服务边界。
